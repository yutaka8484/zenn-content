## 導入:「なんと23の主要オープンソースプロジェクトのうち11は1人または2人で運営されている実態が明らかに」を読んで

はてなブックマークのITカテゴリで、「なんと23の主要オープンソースプロジェクトのうち11は1人または2人で運営されている実態が明らかに」という記事を見かけた（GIGAZINE、https://gigazine.net/news/20261020-open-source-projects/）。多くの現場を支えているライブラリが、実は少人数、場合によっては個人の善意でかろうじて保守されているという話だ。

この記事を読んで思い出したのは、2011年から2019年にかけて製造業の現場で資材購買に関わっていたときの感覚だった。標準品・特注品の工程管理と購買、立ち上げ部材の調達を担当していた中で、「仕入先が一社しかない部品」が止まったときの現場の空気を何度も見てきた。注文は出している、支払いも滞りない、それでも代わりがないというだけで、生産計画全体が止まる。その部品が技術的に特殊だからではなく、単に「もう一つの選択肢を用意していなかった」からだ。OSSの依存ライブラリの話も、技術の話である以前に、同じ構造の調達リスクの話なのではないかと思う。

ソフトウェア側の依存ライブラリ管理は、どうしても「脆弱性が出たらすぐ上げる」「ライセンスがGPLかMITか確認する」という話で終わりがちだ。それはもちろん必要だが、購買の現場で培った目線で見ると、もう一段手前に「この仕入先（＝このライブラリ）は、どれくらい一社依存の状態にあるのか」という評価が必要になる。

## 資材購買で学んだ「一社依存」の怖さ

資材購買の仕事では、部品ごとに「仕入先がどれだけ代替可能か」をいつも気にしていた。同じ部品でも、規格品で複数社から買えるものと、その会社の設備や図面に合わせて作ってもらっている特注品では、止まったときの怖さが全く違う。特注品で仕入先が一社しかない場合、その会社の設備が故障した、担当者が退職した、経営が傾いたというだけで、自分たちの生産計画が止まる。これは仕入先の善意や技術力の問題ではなく、構造の問題だ。

この経験から言えるのは、リスクは「今動いているかどうか」では測れないということだ。今日まで順調に納品されていた部品ほど、代替先を探していないことが多い。問題が起きるのは、順調に見えていた関係が突然途切れたときで、その時にはもう代替先を探す時間的余裕がない。だからこそ購買の現場では、実際に困っていなくても、仕入先ごとに「この一社に依存している度合い」を定期的に見直す作業が必要になる。

OSSの依存ライブラリにも、まったく同じことが言える。GIGAZINEの記事が示しているのは、多くのプロジェクトが「今は動いている」が「代替の担い手を用意していない」状態にあるということだ。メンテナーが1人であること自体が悪いわけではない。問題は、その1人がいなくなったときに何が起きるかを、使っている側が把握していないことにある。

## OSSの依存先にも同じ目で評価する

購買の現場でよく使われていた考え方の一つが、仕入先ごとのBCP(事業継続計画)スコアだ。設備の二重化があるか、代替となる拠点や担当者がいるか、経営状況は安定しているか、といった項目を点数化して、仕入先を「安心して一社に任せられる」か「二社購買すべきか」に分ける。これをOSSの依存ライブラリに当てはめると、次のような項目で評価できる。

| 評価項目 | 購買でのBCP視点 | OSS依存ライブラリでの対応項目 |
|---|---|---|
| 担い手の数 | 設備・人員が一人に集中していないか | コミット権限を持つメンテナーの人数（bus factor） |
| 継続性 | 経営状態・後継者の有無 | 直近1年のコミット頻度、スポンサーの有無 |
| 代替可能性 | 同等品を作れる会社が他にあるか | 同機能を持つ他ライブラリの有無と移行コスト |
| 影響範囲 | その部品が止まると何が止まるか | 自社システムのどの機能がそのライブラリに依存しているか |

この表を見てわかるのは、脆弱性対応やライセンス確認だけでは「代替可能性」と「影響範囲」が見えてこないということだ。この2項目こそ、購買出身者が自然に気にする部分であり、ソフトウェア側の議論でしばしば抜け落ちている視点だと思う。

## 代替・備蓄・多社化という3つの選択肢をソフトウェアに置き換える

資材購買では、一社依存のリスクが高いと判断した部品に対して、おおむね3つの対応を検討していた。代替先を見つける、在庫として備蓄する、複数社から買う体制にする、のいずれかだ。どれを選ぶかは、その部品の重要度と、切り替えにかかるコストのバランスで決まる。

これをソフトウェアの依存ライブラリに置き換えると、次のように対応づけられる。

- 代替先を見つける ＝ フォークする、または別ライブラリへ移行する。メンテナーが実質不在になった時点で、コミュニティがフォークを立てて保守を引き継ぐケースがこれに近い。
- 備蓄する ＝ ベンダリングする。ソースコードを自社リポジトリに取り込んでおき、上流が止まっても最低限のビルドと保守は自分たちでできる状態にしておく。
- 多社化する ＝ 開発元を支える仕入先を増やす、つまりスポンサーシップや寄付を通じてメンテナー自身を支援し、1人体制から複数人体制への移行を後押しする。

どれを選ぶべきかは、購買のときと同じ基準で考えればいい。切り替えコストが低く、代替品の品質にも大きな差がないなら、早めに別ライブラリへの移行(代替)を検討する。切り替えコストが高く、かつ短期的に止まる心配が少ないなら、ベンダリング(備蓄)で時間を買う。自社にとって中核的で、かつエコシステム全体にとっても重要なライブラリであれば、寄付やスポンサーシップ(多社化)でメンテナー体制そのものを支える方が、長期的には安い。重要なのは、この判断を「問題が起きてから」ではなく、依存ライブラリを導入する時点、あるいは半年〜1年ごとの見直しのタイミングで行うことだ。

## 購買台帳にならった「依存先管理表」の作り方

資材購買の現場では、仕入先ごとの状況を一覧できる台帳を持っておくのが基本だった。これをソフトウェアの依存ライブラリにも当てはめ、次のような列を持つ「依存先管理表」を作っておくことを提案したい。

| 列 | 記載内容の例 |
|---|---|
| ライブラリ名・バージョン | 利用しているライブラリとピン留めしているバージョン |
| 用途・影響範囲 | 自社のどの機能がこれに依存しているか |
| メンテナー体制 | コミット権限者の人数、直近のリリース頻度 |
| 重要度ランク | 代替困難かつ影響範囲が広いものを「A」、代替可能なものを「C」など |
| 対応方針 | 代替候補の有無、ベンダリング済みかどうか、寄付の有無 |
| 最終確認日 | この表自体をいつ見直したか |

この表の価値は、個々の行の正確さよりも、「最終確認日」の列を定期的に埋め続けることにある。購買の台帳も、仕入先の状況は常に変わるため、一度作って終わりにはできなかった。依存ライブラリも同じで、半年前は1人運営だったプロジェクトに新しいメンテナーが加わっていることもあれば、逆に主要開発者が退任して体制が薄くなっていることもある。表を作ること自体が目的ではなく、重要度ランクが高いライブラリについてだけ、定期的に状況を確認する仕組みを持つことが本質だ。

## まとめ:明日からできること

GIGAZINEの記事が明らかにしたのは、OSSの多くが少人数の善意に支えられているという事実であり、それ自体は責めるべきことではない。使う側がすべきことは、依存しているライブラリの中から重要度が高いものを数個選び、上の表の形式で「誰が保守しているか」「代替できるか」「止まったらどこが止まるか」の3点だけでも書き出してみることだ。資材購買の現場で一社依存の部品に向き合ってきた感覚からすると、これは一度やれば終わりの作業ではなく、仕入先の状況確認と同じように、半年に一度は見直す前提で続けていくべき仕組みだと思う。
