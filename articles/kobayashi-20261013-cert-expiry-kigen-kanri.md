## きっかけ：ある失効事故を読んで思い出したこと

Zennで「GitHub Pages の証明書失効で Error 526 になったので Cloudflare Pages へ移行した」という記事を読んだ（[該当記事](https://zenn.dev/unsoluble_sugar/articles/6a3fd085a60ec6)）。GitHub Pagesのカスタムドメインに紐づくTLS証明書が更新されず、ある日突然サイトがエラーで表示されなくなったという内容だった。原因そのものは珍しくない。カスタムドメインの証明書発行・更新はホスティング側の自動化に依存しており、何らかの理由でそれが止まると、利用者には「何も変更していないのに落ちた」という形で表面化する。

この話を読んで思い出したのは、ブログ記事にあるような高度な技術トラブルではなく、もっと泥臭い現場の光景だった。筆者は機械メーカーで約8年、生産管理・資材購買の仕事をしていた。標準品・特注品の工程管理と購買を担当する中で扱っていたのが、接着剤やシール材のような「使用期限が決まっている消耗品・特采材料」だった。これらは期限が切れると使えなくなる、あるいは性能保証ができなくなるため、切れる前に次のロットを手配しておく必要がある。当時は手書きの発注書を自作の発注管理ソフトでシステム化し、誤発注と転記の手間を減らす取り組みをしていたが、その根底にあったのは「いつ切れるか分かっているものは、切れる前に手を打つ」という単純な発想だった。

TLS証明書もドメインの更新期限も、本質的には同じ性質を持つ。いつ切れるかは発行時点で分かっている。にもかかわらず、IT現場ではこの「分かっている期限」が台帳化されず、サービス側の自動更新に任せきりになっていて、切れて初めて気づくという事故が繰り返される。この記事では、資材購買で扱っていた期限管理の発想を、証明書・ドメインの運用にどう持ち込めるかを具体的に考えていく。

## 論点1：期限は「知っている」ことと「管理している」ことは別物

資材購買の現場でまず学んだのは、担当者の頭の中に期限が入っていることと、組織として期限を管理できていることはまったく別だという点だった。特定の担当者が「このロットはそろそろ切れるな」と覚えていても、その人が休んだり異動したりすれば、その知識は失われる。だから、期限は属人的な記憶ではなく、誰が見ても分かる台帳に落とす必要がある。

IT運用における証明書・ドメインの期限管理も同じ構造を抱えている。多くの現場では、証明書の有効期限やドメインの更新期限を「設定した人が覚えている」状態で運用されているのではないかと思う。マネージドサービス側が自動更新してくれる場合はそれでも問題が表面化しにくいが、カスタムドメインの設定やDNS側の条件次第で自動更新が失敗することはあり、そうなったときに「誰も気づかない」状態になりやすい。

これに対する考え方として有効なのは、資材購買で使っていたのと同じ台帳形式の管理だ。例えば次のような一覧を、スプレッドシートでも専用ツールでもよいので、ひとつの場所に集約しておく。

| 対象 | 種別 | 発行/更新元 | 有効期限 | リードタイム | 次アクション予定日 |
|---|---|---|---|---|---|
| example.com | ドメイン | レジストラA | 2027-03-15 | 30日 | 2027-02-13 |
| www.example.com | TLS証明書 | Let's Encrypt | 2027-01-10 | 自動更新だが要監視 | 2027-01-03 |
| api.example.com | TLS証明書 | ホスティングB | 2026-12-01 | 手動更新必須 | 2026-11-01 |

台帳があれば、担当者の記憶に依存せず、誰でも「次に何がいつ切れるか」を確認できる。資材購買で消耗品・特采材の使用期限を一覧管理していたのと同じで、台帳の存在自体が属人化を防ぐ仕組みになる。

## 論点2：リードタイムを逆算して「先行手配」する

資材購買で重視していたもうひとつの考え方が、リードタイムの逆算だった。発注してから納品されるまでに一定の日数がかかる以上、「切れてから発注する」のでは遅い。切れる日からリードタイム分を差し引いた日付を「発注すべき日」として設定し、その日が来たら自動的にアラートが上がる、あるいは発注担当者の目に触れるようにしておく。これが先行手配の基本動作だ。

証明書やドメインの更新にも同じ逆算が当てはまる。証明書は発行・反映に多少の時間がかかる場合があり、ドメインの更新はレジストラへの支払いや管理者の承認が絡むことがある。さらに、DNS設定やネームサーバーの変更が絡む場合は反映に時間差が生じることもある。「有効期限の当日に気づく」のでは、リードタイムの分だけ手遅れになりかねない。

具体的には、台帳の「次アクション予定日」を、有効期限からリードタイムを引いた日付で機械的に算出しておくとよい。これは複雑な仕組みを組まなくても、次のような簡単なスクリプトで十分に実現できる。

```python
from datetime import date, timedelta

items = [
    {"name": "example.com (domain)", "expiry": date(2027, 3, 15), "lead_days": 30},
    {"name": "api.example.com (cert)", "expiry": date(2026, 12, 1), "lead_days": 14},
]

today = date.today()
for item in items:
    action_date = item["expiry"] - timedelta(days=item["lead_days"])
    days_until_action = (action_date - today).days
    if days_until_action <= 7:
        print(f"[要対応] {item['name']} : 次アクション予定日 {action_date}")
```

こうした仕組みを監視ツールのcronジョブやCIのスケジュール実行に乗せれば、「期限が近づいたら人間の目に触れる」状態を機械的に作れる。重要なのは複雑さではなく、期限とリードタイムという二つの数字を必ずセットで管理するという発想そのものだ。

## 論点3：自動更新を信頼しつつ「失敗を前提に」監視する

GitHub PagesやCloudflare Pagesのようなサービスは、通常カスタムドメインの証明書を自動更新してくれる。この自動化自体は便利で、基本的には信頼してよいものだと思う。ただし、資材購買の現場で学んだもうひとつの教訓は、「自動化された仕組みも、失敗することを前提に点検する」という姿勢だった。

標準品の発注は仕組み化されていても、特采材料のように仕様変更や取引条件の変化が絡むものは、自動発注のルールから外れて欠品を起こすことがある。だからこそ、自動化された仕組みの外側に、定期的に実際の在庫数量や期限を目視確認する工程を置いていた。自動化を信頼しないという意味ではなく、自動化が想定外の条件で止まったときに気づけるようにしておくという考え方だ。

証明書の自動更新についても同様で、DNS設定の変更、ドメインの移管、レジストラ側の認証切れなど、ホスティングサービスの想定外の条件が重なると自動更新が失敗することがある。これに対しては、外部から定期的に証明書の有効期限を実際に取得して確認する監視を、自動更新の仕組みとは別に持っておくのが有効だ。例えば以下のようなコマンドで、実際にサーバーが提示している証明書の有効期限を確認できる。

```bash
echo | openssl s_client -servername example.com -connect example.com:443 2>/dev/null \
  | openssl x509 -noout -enddate
```

これを日次で実行し、残日数が一定を下回ったら通知する仕組みにしておけば、「設定上は自動更新のはずが実際には失敗していた」という事故を、実際に切れる前に検知できる。自動化を疑うのではなく、自動化の結果を定期的に実測するという発想が、資材購買での在庫確認と同じ構造を持っている。

## まとめ：明日からできること

証明書やドメインの期限切れによる障害は、技術的に難しい問題ではなく、管理の抜けによって起きることがほとんどだと思う。資材購買の現場で扱っていた使用期限管理の発想は、驚くほどそのままIT運用に応用できる。明日からできることとして、まず自社が管理しているドメインとTLS証明書を洗い出し、有効期限とリードタイムを一枚の台帳にまとめてみることをお勧めしたい。その上で、台帳の「次アクション予定日」が近づいたら誰かの目に入る仕組みを、簡単なスクリプトや監視ツールのアラートで用意する。そして、自動更新に任せている部分についても、実際の有効期限を定期的に実測する監視を別途持っておく。これだけで、「気づいたら落ちていた」という事故の多くは防げるはずだ。
