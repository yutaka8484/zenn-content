中小企業のDX現場で、最も残りがちな課題の1つが「設計・判断の記録がバラバラで、後から再利用できない」ことです。現場のメモ、ホワイトボードの写真、Slackのログ…どこに何があるか分からない。数年後、同じ問題にまた出会う。

私は製造業の基幹システム入れ替えを2年半続け、同時に株式会社コバヤシとしてWeb制作・サーバー構築を手掛ける中で、この問題をObsidianとClaude Codeの組み合わせで小さく解消してきました。結論から言うと、“書く”こと自体は継続しつつ、“整形・構造化”はAIに寄せる。そしてその出力を**Docker内のローカルLLMで検証する**――この流れを作ると、開発日誌がそのままナレッジ資産になります。

## 1. なぜ「Obsidian + Claude Code」なのか

私の環境はDocker Composeで動く自宅サーバー（x1lite / Ubuntu 24.04）上に、以下の要素を同居させています。

- Obsidian Vault（Markdownの単なるテキストファイル群）
- Ollama + Open WebUI（ローカルLLM環境）
- Claude Code（AnthropicのCLIツール）

この構成がミソで、**Vaultは“生の記録”として残したまま**、Claude Codeに「Vaultの断片から構造化されたドキュメントを生成して」と依頼します。Web上の外部サービスに社内情報を出さないため、製造業のお客様でも導入しやすい点が大きいです。

## 2. 実際にやっている3ステップ

### ステップ1：Obsidianに“生ログ”をためる
プロジェクトごとにMarkdownを切ります。構成は自由。たとえば：

```text
obsidian/
├── 2026/
│   └── 06/
│       └── 2026-06-11-projectX.md
└── templates/
    └── daily.md
```

`daily.md` は「今日やったこと / 起きた問題 / 次に試すこと」の3行だけでOK。続けやすさが最優先です。

### ステップ2：Claude Codeで構造化ドキュメントを生成
Claude Codeはファイルパスを直接指定できるので、日次ログとプロジェクトメモを投げ込みます。プロンプト例：

```text
obsidian/2026/06/ 以下のMarkdownを読み、
1) 課題一覧
2) 決定事項
3) 次アクション
に整理して projects/projectX/spec.md に出力せよ。
重複は統合し、日付は残すこと。
```

ここがWeb検索とは違う利点です。**プロジェクト内の全ファイルを文脈として扱える**ため、「あの時あちらに書いた制約」をIn contextで反映できます。

### ステップ3：Docker内のOllamaで内容を下書き 검증
生成された `spec.md` を、今度はOllamaのローカルLLMに読み込ませて、「仕様と矛盾する点はないか」「抜けているテストケースは何か」を確認します。外部APIにデータを送らずに、LLMの“第2のレビュアー”として活用できる点が、コンプライアンスの厳しい現場で歓迎されます。

## 3. 仕組みを支える要素

| 要素 | 役割 |
|------|------|
| Obsidian Vault | 生ログの貯蔵庫。検索性も高い |
| Claude Code | ファイルを跨いだ構造化・要約 |
| Ollama + Open WebUI | ローカルLLMによる下書き 검증 |
| Docker Compose | 全要素の統一管理・ ports/volume の分離 |

Docker Composeの `docker-compose.yml` は、volumeでVaultを永続化し、Ollamaのモデルローキャッシュを分離する程度の軽い定義で十分です。私の環境では、x1liteのCPU搭載モデルで日常的な整形処理は事足りています。

## 4. 実際に得られた効果

- **問い合わせ回答時間の短縮**：「以前どの决策をしたか」を過去ログから即座に参照可能に
- **属人化の低減**：Vaultが共通の参照元になるため、担当者ごとの引き継ぎコストが減った
- **開発速度の向上**：Claude Codeによるドキュメント成型が手動の8割をカバー

ただし前提として、“ログが残っていないと始まらない”点は忘れないでください。1行だけでも毎日書く習慣が、最も重要です。
