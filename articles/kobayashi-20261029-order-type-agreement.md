Zenn のトレンドに「4つの受注システムの「注文」を、TypeScript の型で1つにする — null・空配列・ステータスを型で止める」という記事が上がっていた（https://zenn.dev/takutoshuto/articles/1485430c919762）。4つの受注システムが抱える null・空配列・ステータスのばらつきを、型という共通言語で止めるという内容で、技術的な解決としては筋が良いと感じた。

ただ読みながら思い出したのは、2019年から構想を始め、2022年7月から2025年1月まで約2年半かけて実装・移行し、2025年1月に本稼働した基幹システム（ERP）刷新の現場だった。受注〜請求・生産と工程・購買と在庫・会計連携までを範囲とし、部門間の調整と旧システムからの移行を統括する立場で見えたのは、型で止める前にもっと厄介な工程があるという事実だった。「受注」という同じ言葉が、営業・生産・購買でまったく違うものを指していた。型に落とす作業は、その違いにみんなが気づいて、どれを正とするか決めたあとにしか始まらない。

## 「受注」が部門ごとに違う、という現実

ERP刷新のような受注〜請求統合に取り組むと、最初にぶつかるのは技術の問題ではなく言葉の問題だ。営業にとっての受注は「客先に出した見積が確定した瞬間」であり、生産にとっての受注は「工程に投入できる状態になった瞬間」、購買にとっての受注は「部材を手配してよいと判断できる瞬間」を指す。同じ一件の注文でも、部門ごとに「受注」と呼んでよいタイミングがずれている。

これを表にすると分かりやすい。

| 部門 | 「受注」と呼ぶ条件 | 欠けている情報が生む問題 |
|---|---|---|
| 営業 | 見積確定・客先合意 | 仕様未確定でも受注扱いになる |
| 生産 | 図面・仕様確定、工程投入可 | 営業の受注日と着手可能日がずれる |
| 購買 | 納期・数量が確定し発注可 | 特注部材は仕様確定待ちで発注が遅れる |
| 会計 | 検収・請求可能な状態 | 受注〜請求の進捗と実在庫がずれる |

この表の行の数だけ、null になりうる項目・空配列になりうる項目・取りうるステータスの候補が増える。型で null や空配列を止める前に、まずこの表のどの行を「正」とし、どの行を「例外として許容するが型には出さない」とするかを、関係部門の人間同士で決めておく必要がある。決めずに型を書き始めると、型定義そのものが「営業寄り」や「生産寄り」に偏り、別の部門から見て現実と合わない型になる。

## 標準品と特注品を同じ工程表に乗せた経験

生産管理・資材購買の時期（2011〜2019年）には、標準品と特注品という性質の違う注文を同じ工程管理に乗せる仕事をしていた。標準品は仕様が決まっているので、受注した時点で必要な情報がすべて揃っている。一方、特注品は受注した時点では仕様の一部が未確定で、図面確定や客先承認を待ってから工程に投入する。同じ「受注」というステータスの中に、情報が揃っているものと揃っていないものが混在していた。

当時は手書きの発注書を自作の発注管理ソフトでシステム化し、誤発注と転記の手間を減らす取り組みをしていたが、この経験を今振り返ると、標準品と特注品を同じ型・同じ工程表の行として扱うなら、「仕様確定待ち」という状態を型やステータスの値として明示しておくべきだったと思う。空欄や null を「まだ決まっていない」の意味で使うと、プログラム上は合法でも、現場の人からすれば「受注したのに情報がない注文」という矛盾に見える。型で止める対象と、業務上「待ち」として正当に存在してよい状態とを、先に業務側で言葉にして分けておくことが、後工程の混乱を減らす。

## 型に落とす前に、誰と何をすり合わせるか

部門ごとの「受注」の定義がずれたまま型設計に進むと、型は技術的には正しくても、現場の納得感を欠いた仕様書になる。型設計者が先にやるべきなのは、各部門の「受注」の定義を一枚の表に並べ、どの定義を正とするかを関係者の前で明示的に決めることだと考えている。具体的には次のような順番が妥当だろう。

1. 各部門が現状「受注」と呼んでいる条件を、口頭ではなく書面（表）にして持ち寄る
2. 表の行ごとに、どの情報が「受注時点で必ずある」ものかを洗い出す
3. 情報が揃っていない特注品・仕様未確定のケースを、例外ではなく正式な状態として扱うかどうかを決める
4. 決まった定義を、部門の責任者が「この定義でよい」と確認したうえで型に落とす

この順番で合意したあとなら、型はただの技術的な表現になる。例えば受注の状態を次のように表せる。

```typescript
type OrderStatus =
  | "spec_confirmed"   // 仕様確定・工程投入可
  | "spec_pending"     // 仕様未確定（特注品の受注直後）
  | "ready_to_purchase" // 購買手配可
  | "invoiced";         // 請求済み

type Order = {
  status: OrderStatus;
  items: OrderItem[]; // 仕様未確定時は空配列を許容せず、専用の型で表現する
};
```

ここでの `spec_pending` のような値は、技術の都合で生まれたのではなく、業務側が「これは受注として存在してよい状態だ」と認めたから型に書ける。型が業務ルールの後追いであることを忘れると、型を直してもすぐに現実とずれる。

## まとめ：明日からできること

4つの受注システムを型で統一する発想自体は正しい方向だが、着手の順番を間違えると、型が完成しても現場の納得は得られない。まず自分のチームの「受注」や「注文」といった基本語を、部門別に一枚の表にして並べてみることをおすすめする。null になっている項目、空配列になっている項目があれば、それが「本当に無い」のか「まだ決まっていない」のかを、型を書く前に関係者と確認する。合意が先、型はその記録だという順番を守るだけで、刷新や統合の後工程はずいぶん楽になるはずだ。
