## セルフホストを検討する前に整理しておきたいこと

Dify は、プログラミングなしで LLM アプリやワークフローを組めるオープンソースのプラットフォームです。公開情報によれば、公式リポジトリに Docker Compose 一式が用意されており、Linux が動くサーバー 1 台あれば起動できるはずです。木工所のような小規模な製造業でこれを自前で持つ動機は、見積書・図面・取引先情報といった社外に出しにくいデータを、外部の SaaS に渡す前に社内ネットワークで完結させたい、という一点に尽きます。加えて、月額課金の変動に左右されず費用が読める点も現場では効きます。

ただし「起動する」ことと「止まらずに使い続ける」ことは別問題です。専任のインフラ担当を置けない前提だからこそ、着手時にバージョンアップ・バックアップ・監視の三つを設計として決めておく必要があります。ここを曖昧にしたまま現場に配ると、半年後の更新で DB マイグレーションに失敗したり、ディスクが埋まって週明けに全員が使えなくなったりします。以下では、この三点を小規模運用向けに絞った形でまとめます。凝った基盤は不要で、むしろ凝らないことが継続の条件だと考えています。

## Docker Compose の構成とバージョンアップの進め方

公開されている構成では、Dify は `api` / `worker` / `web` / PostgreSQL / Redis / ベクトル DB(Weaviate など)/ Nginx / Sandbox といったコンテナ群で動くとされています。運用で最初に効くのは、イメージタグを `latest` のままにしないことです。`.env` にバージョンを固定し、いつ何に上げたかを記録として残します。

```bash
# .env(抜粋)
DIFY_VERSION=0.15.3
EXPOSE_NGINX_PORT=8080
```

更新は、タグを切り替えてから引き直す手順に統一します。

```bash
cd dify/docker
git fetch --tags
git checkout 0.15.3
docker compose pull
docker compose down
docker compose up -d
docker compose logs -f api | grep -i migrat
```

Dify は `api` 起動時に DB マイグレーションが走るとされているため、メジャー更新の前には必ず後述のバックアップを取り、公式の変更履歴に目を通してから実行します。可能なら別ディレクトリに複製して先に起動し、既存のワークフローが壊れないか確認してから本番へ、という順序にすると安全なはずです。飛び級のアップグレードは避け、一段ずつ上げるほうが原因の切り分けが楽になります。

## バックアップ ― DB とストレージを分けて考える

守るべき対象は性質が違うので分けて扱います。ひとつは PostgreSQL(ワークフロー定義・アカウント・会話ログ)、ふたつめはストレージ領域(アップロードされたファイルやナレッジの元文書)、みっつめはベクトル DB、よっつめは `.env` と DSL エクスポートです。Redis は揮発しても復旧できるので対象外で構いません。

PostgreSQL は日次でダンプし、世代を切ります。

```bash
#!/bin/bash
set -euo pipefail
cd /opt/dify/docker
ts=$(date +%Y%m%d-%H%M)
docker compose exec -T db pg_dump -U postgres dify | gzip > /backup/dify-db-$ts.sql.gz
find /backup -name 'dify-db-*.sql.gz' -mtime +14 -delete
```

ストレージは Docker ボリュームを `restic` などで世代管理します。ベクトル DB は元文書さえ残っていれば再構築できるため優先度は中程度と割り切ります。ワークフロー定義は Dify の DSL(YAML)として定期的にエクスポートしておくと、最悪 Dify 全体を作り直しても業務ロジックだけは戻せるはずです。バックアップは取るだけでなく、四半期に一度は別ディスクへ実際に戻して中身を開くところまでやって初めて「ある」と言えます。

## 監視と障害復旧 ― 手順書に落として属人化を避ける

小規模なので監視項目は絞ります。コンテナの生存、`api` のヘルスチェック、ディスク残量の三つで十分だと考えています。まず Compose の上書きファイルで再起動ポリシーとヘルスチェックを足します。

```yaml
# docker-compose.override.yaml
services:
  api:
    restart: always
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:5001/health"]
      interval: 30s
      timeout: 5s
      retries: 3
```

外形監視は Uptime Kuma を別コンテナで立て、ヘルスチェックの応答が途切れたらチャットやメールに通知させる構成が手軽なはずです。ディスクは残量が一定を切ったら警告するだけの cron スクリプトで足ります。

障害復旧は文章にしておきます。(1) `docker compose down`、(2) DB リストア(`zcat dump.sql.gz | docker compose exec -T db psql -U postgres dify`)、(3) ストレージのリストア、(4) `up -d`、(5) 代表的なワークフローを一本流して疎通確認。年に一度は予備マシンで通しで実施し、所要時間を実測しておくと、いざというとき「何分で戻るか」を経営層に即答できます。

## まとめ

やることは三つだけです。バージョンは固定して更新履歴を残す、バックアップは DB とストレージを分けて世代管理し復元まで試す、監視は生存・ヘルスチェック・ディスクに絞る。Dify 自体はノーコードで現場が触れるのが利点なので、その土台になるインフラはあえて地味で堅実に組むのが正解だと考えています。小規模運用で効いてくるのは、派手な仕組みより「誰がやっても同じ手順で戻せる」状態です。
