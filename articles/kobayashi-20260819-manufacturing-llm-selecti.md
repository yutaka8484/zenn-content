## 現場データをAIに預ける前に立ち止まるべき理由

製造業の現場には、図面の寸法データ、加工機のログ、検品時の不良記録、熟練工の勘所を書き留めたメモなど、社外に出したことのないデータが大量に眠っています。LLMを業務に取り入れようとするとき、多くの企業が最初に直面するのは「このデータをクラウドのAPIに送ってよいのか」という判断です。これは技術選定である以上に、情報管理の方針そのものを問う話です。

クラウド型のLLMは性能もエコシステムも充実しており、導入の手間が小さいという明確な利点があります。一方でローカル型は、社外にデータを一切出さずに済むという安心感と引き換えに、計算資源や運用の手間を自社で負うことになります。どちらが正解というものではなく、扱うデータの性質と自社の体制によって最適解は変わります。以下では、それぞれの特徴と、選定にあたって実務的に効く判断基準を整理します。

## クラウド型LLMの強みと注意点

クラウド型LLMの最大の強みは、最新モデルへのアクセスと運用負荷の低さです。自社でGPUを保有する必要がなく、APIキーを発行すればすぐに使い始められます。図面の要約や報告書のドラフト作成、社内マニュアルの検索補助といった、機密性がそれほど高くない業務であれば、クラウド型を選ぶ合理性は高いはずです。

注意すべきはデータの取り扱いです。多くのプロバイダは学習利用のオプトアウトを提供していますが、契約プランによって挙動が異なるため、利用規約とデータ保持ポリシーを個別に確認する必要があります。また、取引先から提供された図面や仕様書には、自社の判断だけでは外部送信の可否を決められないものも含まれます。以下は、送信前のチェックを機械的に行うための簡易フィルタの例です。

```python
FORBIDDEN_TAGS = ["社外秘", "取引先限定", "個人情報"]

def is_safe_to_send(document_text: str) -> bool:
    return not any(tag in document_text for tag in FORBIDDEN_TAGS)
```

こうした単純なチェックでも、うっかり送信を防ぐ最後の砦として機能するはずです。

## ローカル型LLMの強みと注意点

ローカル型LLMは、モデルを自社のサーバーやワークステーション上で動かす方式で、データが外部ネットワークに出ない点が最大の利点です。加工機のセンサーログや不良品の画像データなど、取引先との守秘義務契約で外部送信が制限されているデータを扱う場合には、この方式が現実的な選択肢になるはずです。

一方で、モデルの性能はクラウド型の最新モデルに一歩譲ることが多く、GPUなどの計算資源への投資や、モデルの更新・保守を自社で担う体制が必要になります。中小製造業にとってこれは軽くない負担です。公開情報を見る限り、Ollamaのようなツールでオープンウェイトモデルをオンプレミスで動かす構成は比較的手軽に試せるようです。

```yaml
# docker-compose.yml の例(公開情報に基づく一般的な構成)
services:
  ollama:
    image: ollama/ollama
    volumes:
      - ollama-data:/root/.ollama
    ports:
      - "11434:11434"
volumes:
  ollama-data:
```

このような構成であれば、まずは小規模な検証環境として立ち上げ、実用に耐えるかを見極めるところから始められるはずです。

## 選定基準:何を軸に決めるか

クラウド型とローカル型のどちらを選ぶかは、感覚ではなく基準を持って判断すべきです。実務上有効だと考えられる軸は次の四つです。第一にデータの機密度で、契約上の制約があるデータはローカル型が前提になります。第二にレイテンシで、現場での即時応答が必要な用途はネットワーク遅延の少ないローカル型が有利です。第三に運用体制で、GPU保守やモデル更新を担える人員がいるかどうかは見落とされがちですが決定的な要因です。第四にコストで、利用量が少ないうちはクラウド型の従量課金の方が総額で安いことも珍しくありません。

これらを一つの表に整理し、案件ごとに機械的に当てはめる運用にすると、担当者ごとの判断のばらつきを抑えられます。重要なのは、最初から完璧な基準を作ろうとしないことです。運用しながら基準そのものを見直していく前提で設計する方が、現実の変化に追随しやすくなります。

## まとめ:小さく試して、境界線を自分たちで引く

クラウド型とローカル型のどちらか一方を全面採用する必要はありません。機密性の低い定型業務はクラウド型、社外に出せないデータはローカル型というように、用途ごとに使い分けるハイブリッドな運用が現実解になるケースが多いはずです。大切なのは、自社が扱うデータのどこに線を引くべきかを、他社の事例をそのまま真似るのではなく、自分たちの取引条件と体制に照らして決めることです。
