## 本番マスタに生まれる「現場の手直し」

Zennのトレンドに、[git archiveとハッシュ一覧の照合で、本番の手修正を上書きしないデプロイスクリプトを作る](https://zenn.dev/airiell/articles/git-archive-manifest-deploy)という記事があった。本番サーバーに入った手修正を、リリース時のアーカイブ展開で誤って消してしまわないように、ファイルのハッシュ一覧を突き合わせてから上書きする、という設計の話だ。これを読んで思い出したのは、基幹システム(ERP)の刷新を終えた後、二次開発を担当していた期間のことだった。

機械メーカーで生産管理・資材購買を約8年担当した経験から言うと、現場が本番マスタに手を入れる理由は、だいたい「正規のルートでは間に合わない例外」に尽きる。標準品の単価は購買部門が決めた通りに流れる。一方で、特定の仕入先からのスポット購買や、立ち上げ段階の部材は、正式な単価改定のサイクルが追いつかない。だから担当者が本番の単価マスタや仕様例外テーブルを直接書き換える。これは怠慢ではなく、現場が業務を止めないための正当な判断だ。基幹システムのPM/PLとして本稼働後も輸出対応の統合や原価計算のシステム化、タイムカードの電子化といった二次開発を重ねていく中で、こうしたマスタデータの扱いには何度も頭を悩まされた。開発側が「正しいデータ」を持っているつもりでも、本番には開発側の知らない事情がすでに書き込まれている。この前提を忘れると、次の一手を間違える。

## リリースがそれを消す仕組み

問題が起きるのは、たいていマスタの一括更新や定期リリースのタイミングだ。開発環境で作ったマスタのテンプレートや、他拠点からのマスタ連携バッチが、本番の該当レコードをまるごと上書きする。手直しをした現場担当者は、自分の修正がどのテーブルのどの列にあるかを開発側に報告していない。また、開発側もどの行が「現場が後から触った行」なのかを区別する手段を持っていない。結果として、リリースのたびに同じ例外対応を現場がやり直す羽目になる。

これを整理すると、マスタ更新で起きる上書き事故は次の3パターンに分けられる。

| パターン | 典型例 | 気づくタイミング |
|---|---|---|
| 全件入替 | 単価マスタをCSVで丸ごと再投入 | 翌月の請求で金額が合わない |
| 定義書きかえ | 仕様例外テーブルをコード側の初期データで上書き | 生産指示が誤った仕様で出る |
| 権限での黒塗り | 現場修正を「不正な直接編集」として巻き戻す運用ルール | 現場が同じ修正を何度も入れ直す |

どのパターンも、根っこは同じだ。「正式なルートで入ったデータ」と「現場が緊急対応で入れたデータ」を、システムが区別していない。区別する仕組みがなければ、リリースする側は良かれと思って正しいデータで塗り替え、現場の判断は気づかないうちに消える。

## git archiveのハッシュ照合から借りる「上書き禁止の境界線」

元記事の発想は、展開前に本番側のファイルのハッシュを取り、リリース対象のアーカイブのハッシュと比較するというものだった。差分がある(=誰かが本番で直接触った)ファイルは、無条件に上書きしない。この「上書き前に差分の有無を確認する」という順序を、ERPのマスタ更新にそのまま持ち込めると考えている。

具体的には、マスタ更新バッチを流す前に、更新対象のレコードについて「最終更新者」と「最終更新日時」を必ず記録しておく。そのうえで、正規の更新経路(購買部門の単価改定フローなど)以外から更新日時が入っているレコードを、一括更新の対象から機械的に除外する。擬似的に書くとこういう判定になる。

```sql
-- 一括更新の対象から「現場が直接触った行」を除外する
UPDATE price_master pm
SET pm.unit_price = src.unit_price
FROM staging_price_import src
WHERE pm.item_code = src.item_code
  AND pm.updated_by IN ('batch_import', 'purchasing_flow')  -- 正規経路のみ上書き対象
  AND pm.updated_at < src.import_started_at;
```

ポイントは、現場の手直しを「例外として許可する」のではなく、「正規の更新経路を通っていないデータは一括更新の対象にしない」という形で線を引くことだ。どちらの言い方も結果は同じに見えるが、後者のほうが運用の現場で説明しやすい。現場は「自分が触った行は消えない」という安心感を持てる。また、開発側は「正規経路のデータだけを確実に更新する」という責任の範囲を明確にできる。

## 定着化フェーズで線を引くときの判断基準

基幹システムの定着化フェーズでは、こうした線引きを後から入れるのは難しい。本稼働後の二次開発で輸出対応や原価計算のシステム化を進めた際も、「どのマスタを正規の更新経路だけに閉じるか」と「どのマスタは現場の直接編集を正式な業務として認めるか」を、機能を追加するたびに確認し直す必要があった。すべてを厳格にロックすると、現場は結局、別のExcelに例外を書き出して管理するようになる。その結果、システムとの差分がまた生まれる。すべてを緩くすると、一括更新のたびに手直しが消える事故が繰り返される。

判断基準として使いやすいのは、「その例外は何日続くか」という時間軸だ。数日で正規の単価改定に吸収される一時的な例外なら、現場の直接編集を許容し、更新日時で一括更新から除外すればよい。逆に、同じ例外が毎月繰り返されるなら、それはマスタ構造の設計が現実に追いついていない証拠だ。そのため、仕様例外テーブル自体に正規の項目として組み込むべきだ。現場の「手直し」を一時的に守る仕組みと、恒常的な例外を正式な仕様に昇格させる仕組みは、別物として用意しておく必要がある。

## まとめ:明日からできること

本番マスタへの現場の手直しは、現場が業務を止めないための正当な判断であり、消してはいけないデータだ。まず着手できるのは、マスタの各テーブルに「最終更新者」「最終更新経路」「最終更新日時」の3列を持たせることだ。これだけで、次の一括更新の前に「正規の更新経路以外から触られた行」を機械的に洗い出せるようになる。そのうえで、頻発する例外は仕様として正式に取り込み、一時的な例外は更新経路の記録で守る。この2本立てを、リリース計画を立てる段階で最初から組み込んでおくことが、現場の信頼を失わない基幹システム運用の土台になる。
