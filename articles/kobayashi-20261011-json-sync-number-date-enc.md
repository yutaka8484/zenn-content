## きっかけと現場の記憶

Zennで話題になった、JSON仕様の曖昧さをテーマにした記事(https://zenn.dev/qnighy/articles/json-ambiguity)を読んで、副業時代に請け負っていたある仕事を思い出した。中小企業の販売管理ソフトから会計ソフトへ、受注・請求データを自動連携させる仕組みを作る仕事である。双方のソフトがAPIとCSVの両方でJSON形式のデータを受け渡せるという話を聞き、「JSONなら仕様が決まっているし楽だろう」と考えていた。しかし実際に動かしてみると、請求金額の末尾が化けたり、納品日が1日ズレたり、取引先名の一部が文字化けしたりという事象が次々に出てきた。

JSONは「仕様がシンプルで明快」という評判の通り、構文自体は確かに単純である。しかし、その単純さの裏には「numberの精度をどう扱うか」「日付という型が存在しない」「文字コードの扱いはJSON側の関心事ではない」という、実装側に委ねられた領域がいくつも残っている。基幹システムの刷新をPM/PLとして担当していた経験から、データ移行では必ず型の突合せを行う習慣がついていたが、JSON連携でも全く同じ注意が必要だと痛感した仕事だった。

## 数値の精度:JSONのnumberの罠

JSONのnumber型は仕様上、言語やライブラリによって内部表現が異なる。多くの実装はIEEE754の倍精度浮動小数点数として扱うため、金額のような小数を含む数値を素朴にやり取りすると、丸め誤差が発生する。

```json
{"amount": 1234.10}
```

この値をJavaScriptで受け取ると `1234.1` に変換され、末尾のゼロが失われる。会計ソフト側が文字列としての桁数（小数点以下2桁固定）を前提にしていた場合、ここで表示がズレる。消費税額を計算して合算するような処理を複数回挟むと、誤差が蓄積して1円単位で合わなくなることもある。

実務的な対策は、金額のような精度が重要な値はJSONのnumberではなく文字列として受け渡すことである。`"amount": "1234.10"` のように文字列化しておけば、送信側の桁数がそのまま保持される。API側がnumber型しか受け付けない場合は、受信直後に文字列化してから計算ライブラリ（多倍長演算や固定小数点演算）に渡すようにする。浮動小数点のまま四則演算をしないことを徹底した方がよい。

## 日付表現:タイムゾーンなしの罠

JSONには日付・時刻専用の型が存在しない。すべて文字列かnumberとして表現するしかなく、その形式は送信側の実装依存になる。実際に連携した際も、販売管理ソフトは `"2025-01-15"` のようなISO 8601形式の日付文字列を送ってきたが、会計ソフト側のAPIは `"2025/01/15"` というスラッシュ区切りを期待していた。さらに厄介だったのは、片方がUTCタイムスタンプ（`"2025-01-14T15:00:00Z"`）で日時を送っており、日本時間に変換すると日付が1日ずれるケースだった。

| 項目 | 販売管理側 | 会計ソフト側 |
|---|---|---|
| 日付形式 | ISO 8601（ハイフン区切り） | スラッシュ区切り |
| タイムゾーン | UTC付きタイムスタンプ | タイムゾーンなしの日付のみ |
| 時刻情報 | 00:00:00固定ではない | 時刻情報を保持しない |

納品日や請求日はタイムゾーンの影響を受けない「業務上の日付」であることが多い。したがって連携仕様を決める段階では、タイムゾーン付きのタイムスタンプではなくタイムゾーンのない日付文字列（`YYYY-MM-DD`）に統一し、どちらのソフトも同じ形式でパースできることを事前に確認しておくべきだった。

## 文字コード:UTF-8とShift_JISの罠

JSON自体の仕様はUTF-8を前提にしている。しかし連携先の会計ソフトが内部的にShift_JISでデータを保持し、API出入り口でのみUTF-8に変換している場合、変換テーブルに存在しない文字（一部の旧字体や外字、丸囲み数字など）が `?` や文字化けに置き換わることがあった。取引先名や品名に特殊な文字が含まれているケースは中小企業の現場では珍しくなく、見た目は正常に見えても一部の文字だけが別の文字に変わっているため、目視チェックだけでは気づきにくい。

対策として、連携テストの段階で意図的に特殊文字（全角英数、丸囲み数字、旧字体の一部）を含んだダミーデータを用意し、往復させて元の文字と一致するかを確認する工程を設けるのが有効である。

## 突合せ・検証の手順

数値・日付・文字コードのいずれも、見た目の確認だけでは漏れが出る。実務では次の手順で突合せを行うのが確実である。

1. 連携対象の全件について、送信前の値から金額・数量のハッシュ値（またはチェックサム）を計算しておく
2. 受信側で同じ計算を行い、ハッシュ値を比較する。1件でも不一致があれば、どの項目が化けたかを個別にdiffで特定する
3. 日付は文字列としてそのまま突合せ、パース結果の比較ではなく生の文字列比較を優先する（パース時に実装差異が吸収されてしまうため）
4. 特殊文字を含むダミーデータで往復テスト（送信→受信→再送信）を行い、何世代経ても文字が変わらないことを確認する

サンプリングではなく全件突合せを基本にしたのは、1円のズレや1文字の文字化けが、月末の帳簿が合わない原因として後から発覚すると、原因調査のコストが連携テストの何倍にもなる経験があったからである。

## まとめ:明日からできること

JSONは構文がシンプルであるがゆえに、数値・日付・文字コードという「型のない領域」が実装依存のまま残っている。販売管理と会計ソフトの連携を検討しているなら、まず金額は文字列で受け渡す、日付はタイムゾーンのないISO形式に統一する、特殊文字を含むダミーデータで往復テストする、という3点を仕様策定の最初に決めておくとよい。接続できることと、数字が正しく一致することは別の話である。
