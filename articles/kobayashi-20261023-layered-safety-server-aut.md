## きっかけ：Rootless DockerとSELinuxの記事を読んで、現場の安全装置を思い出した

Zennのトレンドに上がっていた「Rootless Dockerと学ぶSELinux【初心者向け】」（https://zenn.dev/nexryai/articles/afb828d7dda6b7）を読んだとき、真っ先に思い出したのはコンテナの話ではなく、電気工事士の実技試験で何度も言われた一言だった。「絶縁だけで満足するな、アースも取れ、ブレーカーも入れろ」。root権限をどう扱うか、名前空間をどう切るか、SELinuxでさらに縛るかという判断は、セキュリティの教科書では「多層防御（defense in depth）」という言葉で説明される。だが自分の中では、それより先に現場の感覚の方が強い。一つの対策に全幅の信頼を置かない、というのは資格試験の現場で体に入れた尺度であって、後からセキュリティの用語を当てはめただけのものだった。

ここでは元記事の技術的な内容そのものを解説するのではなく、電気工事・クレーンの資格現場で叩き込まれた考え方が、いまの自社サーバーの権限設計にどうつながっているかを書く。

## 多重防御という発想：電気工事士試験とクレーン資格で叩き込まれたこと

第二種電気工事士の実技では、絶縁被覆・接地（アース）・ブレーカーという三段構えが基本になる。絶縁が万全でも配線を間違えれば感電するし、アースを取っていてもブレーカーの容量が合っていなければ火災になる。どれか一つが完璧でも、残りが抜けていれば事故につながる。玉掛けや小型移動式クレーンの資格でも同じ構造がある。定格荷重を守ることと、合図を目視と声の両方で確認することは、別の対策としてそれぞれ独立に役立っている。荷重計算が正しくても合図を誤れば吊り荷は人に当たるし、合図が完璧でも荷重を超えていればワイヤーが切れる。

この感覚をITの権限設計に当てはめると、「rootを一人で管理する」か「名前空間とSELinuxで二重三重に縛る」かという選択は、本来どちらか一方で済ませる話ではないと感じる。コンテナがrootless化されていても、ホスト側のファイルパーミッションやネットワークのセグメント分けを怠れば、結局どこかの一段が抜けた状態になる。現場で習ったのは、どの対策が「万能」かを探すことではなく、どの対策がどの失敗モードを防ぐのかを一つずつ言える状態を作ることだった。

## 自社サーバーの権限設計にどう持ち込むか

株式会社コバヤシでは、請求書・発注・経費といった業務アプリを自社サーバー上で内製し、紙の領収書をスキャンしてAIで読み取り、会計ソフトへ連携する仕組みを作っている。開発・運用にはClaude Codeも使っている。こうした環境で権限設計を考えるとき、まず自分に問うのは「このプロセスが乗っ取られたら、次に何が起きるか」という一点だ。一つのアプリの実行ユーザーを分け、設定ファイルの読み書き権限を最小化し、バックアップの保存先には業務用アカウントとは別の経路でしかアクセスできないようにする。これは特別な技術ではなく、電気工事の三段構えと同じ発想を、OSのユーザー権限・ファイルシステムの隔離・ネットワークの到達範囲という三つの軸に置き換えただけだ。

| 電気工事・クレーンの多重防御 | サーバー権限設計での対応 |
| --- | --- |
| 絶縁被覆 | アプリごとの実行ユーザー分離・最小権限 |
| 接地（アース） | ファイルシステム・ボリュームの隔離 |
| ブレーカー | ネットワークの到達範囲制限・監査ログ |
| 定格荷重の確認 | 権限の棚卸し（誰が何にアクセスできるか） |
| 合図の二重確認 | 変更時のレビューと監視・通知 |

一人情シス、一人会社という体制では、この全部を同時に完璧にはできない。だからこそ、どの段が今の自分の運用で一番手薄かを棚卸しし、そこから一段ずつ足していくという順番の決め方が、現場で習った「一つに頼らない」という発想の実務的な使い方になる。

## どこまで多重化するかの線引き

ここで悩ましいのは、多重化すればするほど安全になる一方で、運用の複雑さと障害調査の手間も増えるという点だ。電気工事の現場でも、過剰な保護回路を入れすぎると、トラブル時にどの保護が働いて止まっているのかを追うのに時間がかかる。サーバーの権限設計も同じで、SELinuxのような強制アクセス制御を入れれば守りは厚くなるが、設定ミスで業務アプリが動かなくなったときの原因調査は一段複雑になる。

一人で開発・運用まで担う立場では、「守りを厚くする作業」と「異常が起きたときに自分で追える作業」のバランスを取ることが、教科書的な多層防御の説明より重要になる。AIに任せるのは設定の提案やログの一次整理までで、実際にその権限で何が起きるかの最終確認は人がやる、という線引きを自分の中で持っておくのも、資格試験で「最後は自分の目で確認する」と叩き込まれたことの延長だと思っている。

## まとめ：明日からできること

一つの対策で満足せず、別の種類の対策で同じ失敗を二重に防ぐという発想は、電気工事やクレーンの現場では当たり前の前提だが、サーバーの権限設計に持ち込むときは意識的にやる必要がある。まずは今動いている業務アプリの実行ユーザーとファイル権限を棚卸しし、どの段が最も手薄かを一つ特定することから始めるとよい。全部を一度に多重化する必要はなく、どの失敗モードをどの対策で防いでいるかを言葉にできる状態を、一段ずつ増やしていくのが現実的だと考えている。
