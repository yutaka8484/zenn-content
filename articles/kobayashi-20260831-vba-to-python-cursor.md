## 動くけれど、もう誰も直せないマクロ群

木工所の現場では、受注から生産計画、部品表の展開、原価計算までを長年Excelとその上のVBAマクロでまわしてきました。共有フォルダに`.xlsm`が何十個も並び、シート上のボタンを押すと数百行のプロシージャが走ります。動くことは動くのですが、書いた担当者は配置転換で現場を離れ、いまでは中身を追える人がいません。セルの数式と名前付き範囲にロジックが埋め込まれ、テストもバージョン管理もない状態です。

ここで一気に作り直すのは危険だと判断しました。マクロは今日も生産の基準として使われていて、止めれば現場が止まります。そこで方針を「段階移行」に置きました。まずPythonで同じ入力から同じ出力を再現し、旧マクロと並走させて差分を検証し、確認できたものから利用側を一つずつ切り替えていく。Pythonを選ぶ理由は、openpyxlやpandasで同じ`.xlsm`をそのまま読めること、pytestでの検証資産を積み上げやすいこと、小さなサーバーやスケジュール実行に載せやすいことです。大きな成果を一度に狙わず、後戻りできる単位に割って進めます。

## まずVBAを「読める形」に取り出す

リバースエンジニアリングの第一歩は、VBAをファイルとして取り出してGitに入れることです。VBEの参照設定で「Microsoft Visual Basic for Applications Extensibility」を有効にすると、次の小さなマクロで全モジュールをテキスト出力できます。

```vba
Sub ExportModules()
    Dim c As VBComponent
    Dim base As String: base = ThisWorkbook.Path & "\src\"
    For Each c In ThisWorkbook.VBProject.VBComponents
        Select Case c.Type
            Case vbext_ct_StdModule, vbext_ct_ClassModule
                c.Export base & c.Name & ".bas"
        End Select
    Next c
End Sub
```

フォームやシートのコードモジュールも同じ手順で書き出し、`ThisWorkbook`のイベントプロシージャは特に注意して拾います。自動実行の起点がここに隠れていることが多いためです。Gitに入れてしまえば、誰がいつ何を変えたのかという履歴が初めて手に入り、レビューの土台ができます。そのうえで棚卸し表を作ります。列は「入口となるプロシージャ(ボタン割り当て)」「読む対象(セル範囲・シート・名前付き範囲・外部ブック・ODBC)」「書く対象と副作用(シート書き込み・ファイル出力・印刷)」。この対応表がのちの移行単位になります。長いモジュールの要約や`Range()`参照の全列挙は、公開情報によればCursorのAgentモードが複数ファイルを横断して手伝えるはずですが、出力はあくまで索引として扱い、仕様とはみなしません。人が現物と突き合わせて確定させます。

## 仕様書を待たず、入出力を固定する

移行でよくある失敗は、正しい仕様書を書き上げてから実装しようとして止まることです。現実には「現在の挙動」こそが仕様で、その中には既存のバグも含まれます。だから仕様の文章化を待たず、入力と出力の組をゴールデンテストとして固定しました。過去数カ月分の実際の受注シートを入力に使い、旧マクロを走らせた結果を期待値として保存し、Python版がそれを再現できることを条件にします。テストケースは件数を稼ぐより代表性を重視し、通常月に加えて、月末締めの処理、受注ゼロの週、大口が一件だけの週、単位違いが混ざったデータなど、過去に問い合わせや手修正が発生した回を優先して集めます。

```python
import pytest, pandas as pd
from pathlib import Path
from planner import build_schedule

CASES = sorted(Path("tests/fixtures").glob("case_*"))

@pytest.mark.parametrize("case", CASES, ids=lambda p: p.name)
def test_matches_vba_output(case):
    src = pd.read_excel(case / "input.xlsx", sheet_name="受注")
    expected = pd.read_excel(case / "expected.xlsx", sheet_name="計画")
    actual = build_schedule(src)
    pd.testing.assert_frame_equal(
        actual.reset_index(drop=True),
        expected.reset_index(drop=True),
        check_dtype=False, atol=0.5,
    )
```

`atol`はVBAとPythonの丸め差を吸収するための許容値で、意図した差はすべて理由をコメントに残します。検証中に見つかった差分が実は旧マクロのバグだった場合も、まず旧挙動を再現するテストのまま「等価(parity)」を出荷し、バグ修正は別の変更として承認を取ってから入れます。この分離が現場の信頼につながります。

## CursorのAgentモードに任せる範囲、任せない範囲

Cursorは自然言語の指示でファイル横断の編集ができるAIエディタとして知られています。公開情報を踏まえると、取り出した`.bas`群とゴールデンテストを渡し、「1プロシージャずつPythonに実装し、そのテストが通るまで直す」という進め方ができるはずです。出力のぶれを抑えるため、ルールファイルを置いておきます。

```
# .cursor/rules/migration.md
- 参照してよい仕様は tests/fixtures 配下のゴールデンデータのみ。
- 1PR = 1プロシージャ。既存VBA挙動の再現に限定し、バグ修正は含めない。
- pandas / openpyxl を使用。セル番地は constants.py に集約しハードコードしない。
- 生成後は pytest -q を実行し、失敗時の差分を必ず貼る。
```

実装は小さなループでまわします。1プロシージャを選び、エージェントに実装させ、`pytest -q`を実行し、落ちた差分を貼らせて修正させ、通ったらコミットする。1コミットが1プロシージャに対応していれば、あとで問題が出ても切り戻しやすくなります。任せないのは判断です。許容誤差の決定、差分がバグかどうかの見極め、切り替え順序、そして稼働中のマクロに触れる作業。エージェントは機械的な翻訳と参照の列挙が得意で、リスクの判断は人が持ちます。「テストを通す」ことに最適化したエージェントは期待値をハードコードしかねないので、レビューは全差分に対して行い、テストにはエージェントへ渡さない検証用ケースを別途混ぜておきます。

## 移行の順番と、撤退ラインを先に決める

切り替えの順序はリスクの低いものからにしました。最初は読み取り専用の帳票(比較が容易)、次に原価計算、最後に書き戻しを伴う生産計画です。数サイクルはPython版と旧マクロを同時に走らせる「シャドー運用」とし、毎回の実行結果を突き合わせ、差分がゼロか、説明可能な状態がN期連続で続いたときだけ利用側を切り替えます。`.xlsm`は少なくとも四半期は退避先として残します。

同時に、着手前に撤退ラインを言語化しておきます。あるモジュールで定めた週数内に等価へ到達できなければ、いったん止め、理由を記録してマクロを使い続ける。無理に押し切らないことを最初の合意事項にしました。段階移行の利点は、全体が終わる前から価値が出ることです。ゴールデンデータとテストは、それ自体が誰でも読める生きた仕様書になり、共有フォルダには無かった変更履歴がGitに残ります。ブラックボックスが、少しずつ現場の資産に戻っていきます。
