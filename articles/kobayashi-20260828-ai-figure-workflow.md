## 現場マニュアルに載せる図が、いつも足りない

株式会社コバヤシは大阪・八尾で木工加工を手がける町工場で、製造業のデジタル化を自社で進めている。マニュアル整備を始めると、必ず図が足りなくなる。加工手順、治具のセット位置、安全上の注意喚起。文章だけでは現場に伝わらない。かといって設備の写真を撮ると背景に他の機械や書類が映り込み、そのまま配れない。手描きのイラストは分かりやすいが1枚に30分かかり、10工程あれば半日が消える。外注は1枚数千円で、修正のたびに数日待つことになる。技術ブログ用のサムネイルやOGP画像も事情は同じで、本文を書き終えてから画像で止まる。

欲しいのは「そこそこの図を、大量に、早く」揃える仕組みだ。1枚の傑作ではなく、100枚の及第点。AI画像生成はこの用途と相性がよいはずだが、単発でプロンプトを打つだけでは線の太さも配色も毎回変わり、マニュアル全体で見るとちぐはぐになる。ツール選定と、その前後の工程まで含めた制作ワークフローとして設計する必要がある。本稿では公開情報をもとに検討した組み立て方を、木工所の実務目線で整理する。

## ツールはテキスト描画・コスト・比率制約で見る

マニュアル用途なら評価軸を絞れる。第一にテキスト描画。図中に「面取り0.5」「バリ取り」といった日本語ラベルや寸法を入れたいので、文字が崩れると使えない。第二に生成コストと速度。数十枚を試行錯誤するため、1枚が安く速いほど試行回数を稼げる。第三が画角の自由度で、マニュアルはA4縦、サムネイルは16:9と用途で比率が変わる。

公開情報によると、GoogleのGemini Image Flash-Lite系にあたる「Nano Banana 2 Lite」は高速・低コストで、テキスト描画も改善されているとされる。一方でアスペクト比が固定される制限があるという。ならば生成は既定比率で受け取り、トリミングや余白追加は後工程で機械的に整える前提を置くのが現実的なはずだ。弱点を運用でふさぐ発想で「比率は後で直す」と決めれば、本質的な軸で選定できる。判断は印象論を避け、同じ10プロンプトを複数ツールに投げて記録を残す。

```csv
tool,prompt_id,text_ok,seconds,cost_rank,note
tool-a,p01,1,4,low,ラベル1文字欠け
tool-a,p02,1,5,low,OK
tool-b,p01,0,9,mid,漢字が崩れる
```

この形式で全プロンプト分を残し、文字の崩れ率と1枚あたり時間で比べれば、選定の根拠が後から検証できる。

## プロンプトをテンプレート化してスタイルを固定する

単発プロンプトの弱点は再現性のなさだ。マニュアル全体で見た目を揃えるには、スタイル部分を固定したテンプレートに内容だけ差し込む。木工所の図なら「白背景・フラットな線画・アイソメ視点・注意箇所だけ橙」といった基準を決め、共通ブロックとして持つとよい。

```yaml
# style/base.yaml
style: >
  flat vector line illustration, white background, isometric view,
  2px uniform outlines, muted palette, hazard parts in orange (#E8630A),
  no photorealism, no text unless specified
negative: "photo, shadow, gradient, clutter, watermark, hands"
render: { size: 1024x1024, seed: 42 }   # 比率は後工程で調整
```

```yaml
# jobs/wm12_step03.yaml
extends: style/base.yaml
subject: "clamping a wooden panel onto a jig with a toggle clamp"
labels_ja: ["パネル", "トグルクランプ", "位置決めピン"]
callout: "指をクランプ可動部に置かない"
aspect_target: "A4-portrait"
```

内容側には工程番号・被写体・ラベル・注意文だけを書く。現場担当者はこの数行を埋めるだけでよく、英語のプロンプト作法を覚えなくてよい。テンプレートをgitで管理すれば、誰がなぜその色にしたかを履歴で追える。線を太くしたい時はbase.yamlを1箇所直して全図を再生成すれば揃う。レビューも差分だけ見ればよく、属人化しにくい。次のマニュアルは既存ジョブの流用で立ち上がる。

## 生成から配置、レビューまでを一本の流れにする

1枚ずつ手作業で生成・保存・貼り付けしていては量産にならない。工程表のCSVを入力に、生成・比率調整・命名・配置をスクリプトで流す。

```python
# build_figures.py（抜粋・擬似コード）
import csv, json, pathlib

OUT = pathlib.Path("figures")

for row in csv.DictReader(open("manual.csv")):
    raw   = generate(row["job"])                 # 既定比率で受け取る
    fixed = to_aspect(raw, row["aspect"])        # 余白かトリミングでA4縦/16:9へ
    name  = f'{row["doc"]}_{int(row["step"]):02d}.png'
    (OUT / name).write_bytes(fixed)
    print(json.dumps({"file": name, "job": row["job"],
                      "prompt_hash": row["hash"]}, ensure_ascii=False))
```

ファイル名は「文書ID_工程番号」で機械的に決め、Markdownからは `![](figures/wm12_03.png)` で参照する。生成物にはプロンプトのハッシュとジョブ名をログに残し、「どの指示で出た図か」を後から追えるようにする。ここまで自動化しても採否は人が見る。生成物をコンタクトシートに並べて担当者が○×を付け、×の行だけCSVを直して差分実行すれば、100枚中10枚の作り直しが数分で終わるはずだ。安全に関わる図はAIがボルト本数や刃物の回転方向を取り違えることがあるため、現物と照合し、必要なら写真や手描きに差し替える。

## 事実性と権利のチェックを外さない

量産フローで一番危ういのは、それらしく見えて間違った図が混じることだ。だから生成物は「清書された下書き」として扱い、工程を知る人間が確認する前提を崩さない。チェックは口頭ではなくテンプレート化し、プルリクエストに載せて漏れをなくす。

```markdown
## 図レビュー チェックリスト
- [ ] 部品の数・向き・比率が現物と一致
- [ ] 日本語ラベルの誤字なし／用語が社内表記と一致
- [ ] 実在の人物・他社ロゴ・商標が写り込んでいない
- [ ] 使用ツールの利用規約で商用利用が許諾されている
- [ ] 元プロンプトとジョブ定義をリポジトリに保存済み
```

権利面は、使う各ツールの利用規約を都度あたり、商用可否と生成物の帰属を規約本文ごと記録しておく必要がある。まとめ記事の要約だけで判断しないほうが安全なはずだ。これらをレビュー必須にしておけば、確認を通らない図がマニュアルへ入ることを防げる。テンプレートとチェックリストは、量産して初めて言語化できる暗黙のルール——線の太さ、注意色の使いどころ、ラベル位置——を次の担当者へ引き継ぐ器にもなる。ツールが入れ替わっても、この器が残れば見た目とレビュー基準は保てる。

## まとめ

木工所の実務から見ると、AI画像生成は「1枚の質」より「揃った図を大量に、早く」という課題に効く。鍵はツール単体の性能ではなく、スタイルを固定したテンプレート、生成から配置までのスクリプト、事実性と権利の人手チェックを一続きのワークフローとして組むことだ。比率固定のような弱点は後工程で吸収すると割り切れば、選定はテキスト描画とコストという本質的な軸に絞れる。始め方は小さくてよい。まず10プロンプトの比較記録を取り、テンプレートを1つ作り、スクリプトで5枚だけ流してみる。並んだ結果を見て自社の基準を決め、次のマニュアルからテンプレートを流用していく。最初から完璧な基準を作ろうとせず、量産しながら固めていくのが現実的だと考えている。外注費や制作時間の削減は結果としてついてくるが、狙いはむしろ、図が理由でマニュアル更新が止まらない状態をつくることにある。現場の手順が変わったその日に図も差し替えられる。そこまで来て初めて、マニュアルは生きた文書になる。
