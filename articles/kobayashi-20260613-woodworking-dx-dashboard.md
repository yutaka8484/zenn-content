# 木工所の“紙の管理”を脱ぎ捨てた：受注から生産管理までDockerで1本化した話

2026年、私は**木工所の事業承継**に関わることになった。

そこで最初に直面したのが、古いExcelと紙の台帳に依存した業務フローだった。受注管理は1つのファイル、生産管理はまた別のファイル、在庫は應用帳票…。担当者が変わるとそのルールも曖昧になる。

この記事では、**Docker + SQLite + 最小のWeb UI** で、見積→受注→生産管理→在庫→納品までを“押したり塗ったりしない形”でどう刷新したかを書く。

## 1. 現場が“変えたくない”をどう越えるか

製造業の workflow は、長年の試行錯誤で紙になってきた。  
特に MTO（受注生産）の現場では：

- 見積書の台帳管理（案件番号、材種、寸法、納期）
- 進捗のホワイトボード管理
- 検品後の出荷リスト

この3つをバラバラに管理しているのが普通だった。  
「システム化したい」と言われると、現場は「忙しいから面倒」と反応する。

**コツは「全面置換え」ではなく「今まで通りの手順を、1本の画面で追えるようにする」こと**。  
UI の変更は最小に、データの所在だけ整理する方針にした。

## 2. Docker でmini基幹システムを作った理由

自宅の x1lite サーバーは Docker 環境が整っていた。  
ここに SQLite をデータストアとする小さな Web アプリを載せた。

### アーキテクチャ（超.minimal）
```
app (FastAPI + SQLite)
 └─ 受注 / 見積 / 生産指示 / 在庫 を1DBで管理
frontend: 必要最小限の CRUD 画面
infra: Docker Compose で app + frontend + backup cron の3要素
```

選定の理由：

- **SQLite**: 小規模ならファイル1つで管理できる。バックアップも `cp` で良い
- **Docker Compose**: 環境差分を無くし、後任者にも渡しやすい
- **FastAPI**: 型安全 + ドキュメント自動生成で、実装の共有が楽

## 3. 実際に作った画面：受注登録フロー

```python
# 受注登録API（最小の設計）
@app.post("/orders")
def create_order(order: OrderIn):
    order_id = generate_order_id()  # 例: ORD-2026-0613-001
    db.execute(
        "INSERT INTO orders (id, customer, product, deadline) VALUES (?, ?, ?, ?)",
        (order_id, order.customer, order.product, order.deadline)
    )
    return {"order_id": order_id, "status": "created"}
```

現場で必要な入力項目だけを4つに絞った：

- 顧客名
- 品名（材種・寸法）
- 数量
- 希望納期

これだけの画面でも、受注一覧で案件が埋もれなくなるだけで、**進行管理の負担が半分以下**になったと現場担当者からもらった。

## 4. 生産指示→検品→出荷までの流れ

受注確定後は自動で「生産指示書」をPDF化、  
検品完了後は在庫テーブルを更新、  
出品時には送り状番号を紐付ける仕組みも追加した。

特に **寸法入力の補助** は重要だ。木工所では各製品の実寸が変わるため、都度計算が必要になる。Dimensions（mm単位）の入力欄に簡易計算を仕込むことで、ミスを減らした。

## 5. 失敗したこと・直したこと

- **最初はクラウドDBにした** → 現場のインターネット回線が不安定で却下
  - → ローカル SQLite + 夜間バックアップスクリプトに変更
- **画面をrichにしすぎた** → 担当者が敬遠
  - → CRUD + 一覧 + 印刷ボタンのみまで削った
- **権限管理を入れすぎた** → 担当者が「何をしても良いかわからない」と混乱
  - → 帳票閲覧は全員、編集は班長のみ、という単純ルールに統一

## 6. 事業承継とITの関係性

事業承継の局面では、**設備と同じようにデータと手順も引き継ぐ**必要がある。  
私がやったことは：

- システムの内容をPDFドキュメント化（Flow + データ項目 + メンテ手順）
- 半年に1回の操作研修（現場責任者に対して実施）
- Docker Compose ファイルは1ファイルで、`git clone` → `docker compose up` で動く状態を維持

システムの心配より、**“もし自分が倒れたら、誰かがこれを再現できるか”** を先に考えるのが正解だった。
