# テストを書けない現場に、 Claude Code で "安心できるリリース" を入れた話

私の仕事の大半は **中小製造業の現場改善** だ。ある木工所の基幹システム入替PJでは、生産管理・受注・請求のデータがSQLite/Docker環境で動いている。そのとき困ったのが「本番変更の不安」だった。今まで「動いているから」で済ませてきた現場を、どうやって変えるか。

この記事では、**Claude CodeとDocker、Pythonで回す最小限のリリース前検証フロー**を、実際に試しながら紹介する。誰でも真似できる「小さな自動化」を目指す。

## 1. 現場で自動化に踏み出せないわけ

中小製造業の現場では

- テスト環境がない
- 担当者が手作業で差分を確認
- 本番が動いているから「変更しない方が安全」

というジレンマが生まれる。私の例でも、システム入れ替え後に「やっぱり動かない」ことが何度か起きた。小規模で一人担当だと、失敗した瞬間のリスクが自分に跳ね返ってくるため、ついつい無理のない範囲で済ませてしまう。

## 2. Claude CodeとPythonで作った最小フロー

まず **変更を検知し、テスト → 差分確認 → 手動承認** の順で流すようにした。本番サーバーx1liteではPythonスクリプトとDocker Composeで管理しているため、次のコンポーネントだけで動かせる。

### 処理の流れ

1. git push 後、変更ファイルの一覧を取得
2. `docker-compose exec app python -m pytest tests/` を実行
3. 結果を `release_report.md` に保存
4. レポートをSlackに送信し、リリース判断は人間が行う

**実際に使ったPythonのメイン処理（最小版）**

```python
import subprocess
from pathlib import Path

REPORT = Path("release_report.md")

def run_tests() -> bool:
    result = subprocess.run(
        [
            "docker-compose",
            "exec",
            "-T",
            "app",
            "python",
            "-m",
            "pytest",
            "tests/",
        ],
        capture_output=True,
        text=True,
    )
    REPORT.write_text(f"# テスト結果\n\n```\n{result.stdout}\n```\n")
    return result.returncode == 0

if __name__ == "__main__":
    ok = run_tests()
    raise SystemExit(0 if ok else 1)
```

大事なのは **「先にテストありき」** ではなく **「リリース前に判断材料を1つ増やす」** こと。私はこれを「Claude Codeの設計支援」と組み合わせた。エージェントに実装案を出させ、差分を確認してからにすることで、書くスピードと安全性を両立している。

## 3. 現場で得られた効果と注意点

私が実際に感じたメリットは3つある。

- **失敗箇所が明確になった**：pytestの結果があるだけで、原因の切り分け時間が減った。
- **チームの心理的抵抗が減った**：テスト結果という共通言語ができると、判断が早くなる。
- **Claude Codeとの分担が生まれた**：型やテストケースの草案を生成させ、私は本番運用条件と合致するか確認する。

反面、**テストの網羅性より“壊れていないことを示す1本”が先に必要**だと学んだ。完璧から始めるのではなく、リリース前の安心感を積み重ねる。

## 4. 明日から真似できるステップ

1. まず「リリース前の目視チェック」をドキュメント化する。
2. 次にPythonでテストコマンドを実行するだけのスクリプトを追加する。
3. 結果をレポートに保存し、当日の作業としてSlack等で共有する。
