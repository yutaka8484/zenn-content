# 個人開発サーバーの通信をSniffnetで可視化する手順

中小企業の現場でもサーバー運用は避けて通れない。受注管理や生産管理、勤怠電子化など、社内システムが増えるほど「どの端末がいつ、どこへ通信しているか」を把握したい場面が増える。

本記事では、OSSのネットワーク監視ツール「Sniffnet」で開発サーバーの通信を可視化する構成を、公開情報をもとに設定の勘所と効果として整理する。※当社ではまだ導入しておらず、検討記事である。

## なぜSniffnetなのか

- **GUIで迷わない**: Wiresharkは高機能だが、業務に必要な“誰がどこへ、どれだけ送受信しているか”の把握には学習コストが高い。
- **リソースが軽い**: Rust実装のデスクトップアプリで、開発用PC上でも負荷が小さい。
- **クロスプラットフォーム**: 開発環境も検証機もWindows/macOS/Linuxが混在しがちな現場で選びやすい。

私の場合、基幹システム入れ替えPJでは「基幹システムAPIのプログラミング連携がなぜか遅い」「同一ネットワーク内の別サーバーが予期しない頻度で外部と通信している」という場面に直面した。その調査にはSniffnetのような可視化ツールが有効だ。

## Docker環境でSniffnetを使う場合の注意点

Sniffnetはデスクトップアプリだが、開発サーバー上の通信を確認するには、**監視対象のネットワークNamespaceからは、別のマシンのSniffnetから行うか、`--net host` 相当の共有が前提になる**。

実運用では ENV/ツール検証、開発/検証など段階的な導入で確実に進めた。テストは Docker 環境で再現性高く確認し、動作が安定してから検証/本番に展開する手順で進める。

## 期待できる効果

1. **原因が“通信”にあることが分かり、調査時間が減った**
   基幹システムを動かす乏For部の遅延調査で、特定のバッチ処理が外部APIに毎分リクエストを送っていた特定でき、後続のチューニングに進めた。

2. **エンジニア以外でも説明が容易**
   「TTCPやWiresharkは説明が難しい」という製造部門の担当者でも、Snapshotの通信量グラフと接続先一覧を見れば状況を理解できる。

3. **運用地図として再利用しやすい**
   一度可視化した結果は、社内の“標準監視セット”として残せる。今回の評価をベースに、ホワイトリスト運用やアラート条件の検討を始めている。

Sniffnetはあくまで“可視化”の第一歩。見えた情報を、**ルール見直し、監視条件、担当者への説明資料**へと翻訳する仕組みがDXの本質だと考える。

## 株式会社コバヤシへの相談

木工所の製造・図面・工程管理の現場などでも、社内システムの通信可視化やDX推進が必要な場面は多い。まずは小さく1時間で動くプロトタイプを作り、効果検証から始める運用を提案している。
