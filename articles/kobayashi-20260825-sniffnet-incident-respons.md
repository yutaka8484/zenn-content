## 中小製造業のネットワーク監視という盲点

株式会社コバヤシは大阪・八尾の木工所で、製造現場のデジタル化を自社で進めています。図面管理や在庫管理のためのサーバーを社内に置いていますが、こうした自前運用のサーバーは「立てて終わり」になりがちで、通信状況を継続的に見る仕組みまで手が回らないことが多いのが実情です。ファイアウォールのログはあっても、日常的に眺める習慣がなければ異常は見逃されます。

きっかけは些細なことでした。社内サーバーの帯域使用量がいつもと違うグラフを示していたため、原因を切り分ける必要が生じました。Wiresharkはパケット解析には強力ですが、日常監視のために毎回フィルタを組んで読み解くのは負担が大きく、非専任の担当者が継続運用するには不向きです。そこで導入したのが、GUIが直感的でリアルタイム可視化に強いオープンソースツール「Sniffnet」でした。この記事では、Sniffnetを使って実際にどう調査し、どう対処したかを時系列で記録します。

## Sniffnetでの通信可視化と第一次スクリーニング

Sniffnetは接続先IP・ドメイン・地理的位置・アップロード/ダウンロード量をリアルタイムで一覧表示してくれるため、まず「どのアプリが」「どこへ」「どれくらいの量を」送っているかを一目で把握できます。自社サーバーでは、業務アプリケーションが通常アクセスする範囲(社内クライアント、クラウドバックアップ先、既知のSaaS)をあらかじめ把握していたので、そこから外れる接続先が視覚的に浮き上がってくる状態を作りました。

実運用では、Sniffnetの通知機能とIPブラックリスト機能を組み合わせています。既知の悪性IPレンジや、業務上まったく心当たりのない海外ホスティング事業者のASNを手動でブラックリストに登録し、該当通信が発生した際にアラートが上がるようにしました。設定はGUI上で完結しますが、イメージとしては以下のような判定ロジックが動いています。

```
if (接続先IP in blacklist) or (接続先が業務ホワイトリスト外 and 通信量 > 閾値):
    notify(接続先, プロセス推定, 通信量, 継続時間)
```

このスクリーニングによって、深夜帯に断続的に発生していた小容量・高頻度の外向き通信を発見しました。業務時間外にサーバーが自発的に外部へ通信する理由は通常ないため、これが最初の異常検知のトリガーになりました。

## ログ突合によるプロセス特定と原因切り分け

Sniffnet単体では「どのプロセスが」その通信を発生させているかまでは特定しきれない場面があったため、OS側のログと突き合わせる作業を行いました。Linuxサーバーであれば`ss`や`lsof`で接続元プロセスを特定し、Sniffnetで得た接続先IP・ポート・タイムスタンプと照合します。

```bash
# 該当時刻付近の外向き接続とプロセスの対応を確認
sudo ss -tpn | grep <怪しい接続先IP>

# 該当プロセスが正規のものか、改ざんされていないかを確認
ps -fp <PID>
sha256sum /proc/<PID>/exe
```

この突合の結果、原因は外部からの侵入ではなく、社内で試験導入していた監視系エージェントの設定ミスで、意図しない外部エンドポイントへ定期的にハートビート通信を送っていたことが判明しました。悪意ある通信ではなかったものの、「なぜ気づけなかったのか」を振り返ると、通信の可視化と業務上の通信パターンの棚卸しを普段からしていなかったことが根本原因でした。結果として、該当エージェントの設定を修正し、以後は通信先ホワイトリストをドキュメント化して定期的に見直す運用に変えています。誤検知であっても調査プロセス自体は本物のインシデント対応と同じ手順を踏むべきだと考え、今回も省略せずに一通りの切り分けを行いました。

## 再発防止のための運用設計

一度きりの調査で終わらせず、継続的な仕組みに落とし込むことを重視しました。具体的には、業務上正当な通信先をホワイトリストとして明文化し、それ以外への通信は原則アラート対象とする方針に切り替えています。Sniffnetの通知機能はデスクトップアプリとしての利用が前提になるため、常時起動しておく端末を決め、担当者が交代で確認する運用ルールを作りました。

また、調査で得た知見はその都度ドキュメント化しています。異常時にどのコマンドで何を確認したか、判断基準は何だったかを残しておくことで、次に似た事象が起きたときの初動が格段に速くなります。中小企業では担当者が一人しかいないケースも多く、属人化した勘に頼った対応は継続性がありません。ツールを導入すること自体よりも、「異常とは何か」を定義し、それを検知・記録・是正するサイクルを回せる形にすることの方が、長期的には効いてくると実感しています。

## まとめ

Sniffnetのようなツールは、専任のセキュリティ担当者がいない中小製造業にとって、日常的な通信監視のハードルを大きく下げてくれます。今回のケースでは実害のある侵入ではありませんでしたが、可視化がなければそもそも気づけなかった事象です。重要なのは、ツールを入れて終わりにせず、検知から原因特定、是正、再発防止のサイクルを自社の運用に組み込むことだと考えています。
