## はじめに: データの安全性と利便性の矛盾  

製造業の現場では、図面や顧客情報などのデジタルAssetが日増しで重要性を増しています。しかし、これらのデータを「安全に保つ」と「どこからでも使えるようにする」という2つの要件は、技術的にも運用的にも困難なバランスです。外部クラウドに預けることで利便性は高まりますが、情報漏洩のリスクが伴います。一方、ローカル保存のみに頼る場合は、物理的な媒体の損傷やアクセス制限が問題に発展します。  

当社は創業前から、この矛盾を解消する技術設計に注力しました。結果として、社内にデータを一元化しつつ、安全な通信ネットワークを構築する仕組みを実現しました。本記事では、このシステムの技術的設計思想と実装詳細、運用中に得た教訓を解説します。  

## 社内データ保管庫の構築: NASサーバーを中心とした設計  

### ハードウェア選定とソフトウェア構成  
まず、データの一元化を実現するため、社内に専用のNAS（ネットワークアタッチドストレージ）サーバーを構築しました。選択基準は以下の通りです：  

- **信頼性**: RAID 1（ミラーリング）構成でディスク障害に備える  
- **拡張性**: 4ベイ構造で将来的なストレージ増設を視野  
- **電源冗長化**: ダブル電源設計で停電時のダウンリスク低下  

OSはDebian GNU/Linuxを採用し、Sambaを用いたファイル共有サービスを構築しました。アクセス権限はActive Directoryと統合し、ユーザーごとにディレクトリの読み書き権限を厳格に設定しています。  

```bash
# Samba構成例（/etc/samba/smb.conf)
[global]
  workgroup = WORKGROUP
  server string = DataServer
  security = user
  map to guest = bad user

[DataShare]
  path = /data/shared
  valid users = @data_users
  force group = data_users
  read only = no
  browsable = yes
```

### 自動バックアップシステムの実装  
データの物理的安全性を確保するため、毎日深夜にZFSファイルシステムのSnapshot機能を利用した自動バックアップを実行しています。Backupタスクはcronで管理し、7日間分の履歴を保持する仕組みとしました。  

```bash
# crontab -e
0 3 * * * /usr/local/bin/data_backup.sh
```

```bash
#!/bin/bash
# data_backup.sh
zfs snapshot -r pool1/data@daily_$(date +%F)
zfs list -t snapshot | grep 'daily_' | head -n -5 | awk '{print $1}' | xargs -r zfs destroy
```

この設計により、誤削除やハード故障にさえ対応可能なデータ管理体制を実現しました。  

## 事務所と工場の安全な接続: Tailscaleで構築するSD-WAN  

### Tailscaleの導入理由とネットワーク設計  
2地点間の安全な接続には、WireGuardプロトコルを基盤にしたTailscaleを採用しました。理由は以下の3点です：  

1. **Zero Trustアーキテクチャ**: すべての通信を暗号化し、IPアドレスではなく認証ベースでアクセス制御  
2. **簡易的な導入**:専用回線の工事不要で、既存のインターネット回線を活用  
3. **拡張性**: 将来の拠点増設にも対応可能  

ネットワーク構成は以下の通りです：  

```
[事務所NAS]  
   |  
[Tailscaleゲートウェイ] ←→ [工場PC]  
   |  
[工場NAS（将来的な拡張用）]
```

### 実装詳細と設定例  
Tailscaleの導入手順は以下の通りでした：  

1. 管理PCにTailscale CLIをインストール  
2. NASサーバーにWireGuardサブインターフェースを設定  
3. TailscaleダッシュボードでIPアドレスの固定とアクセス制限を設定  

```bash
# Tailscaleアカウントにログイン
sudo tailscale up -url=https://w.x.y.z:41641/xxxxx

# サブネットの設定例
sudo tailscale set --subnet=192.168.100.0/24
```

この構成により、工場の作業員が社内ネットワークに接続する際、TailscaleのTLS暗号化トンネルを介して安全にアクセス可能になりました。  

## 実運用でハマったポイントと解決策  

### ハードウェアの環境依存性  
NASサーバー構築時に選択したマザーボードが、特定のSSDとの互換性に問題を抱えていた事例があります。初期のテストでは問題が見られませんでしたが、本運用開始後に偶発的なディスク認識失敗が発生。原因特定のため、dmesgログの詳細分析とマザーボードのBIOSアップデートにより解決しました。  

### ネットワークの帯域制限  
Tailscaleを介する通信では、初期設定ではMTU（最大転送単位）がデフォルトの1450バイトで設定されていましたが、図面ファイルの転送時にタイムアウトが頻発。MTU値を1380に調整し、パケットフラグメントの発生を防ぐ対策を施しました。  

```bash
# MTU設定変更例
sudo ip link set dev tailscale0 mtu 1380
```

### まとめ: 技術設計の本質的な問い  

このシステム設計の最中、常に問い続けたことがあります。「データの安全性と利便性のバランスは、技術的選定だけでなく、社員の行動様式とも密接に関係する」という認識です。  

- **技術的選定**: 自社管理サーバー×Tailscaleの組み合わせで、外部依存を最小限に抑えつつ柔軟性を確保  
- **運用面**: 自動化されたバックアップと、定期的なセキュリティ演習で人的リスクを軽減
