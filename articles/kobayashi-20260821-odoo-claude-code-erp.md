## 前職のシステム入替から見えた「内製」という選択肢

前職の機械メーカーでは、受注から請求までを含む基幹システムの入替をプロジェクトマネージャーとして率いました。パッケージソフトの標準機能に業務を合わせる調整に2年半を費やし、そこで得た結論は「カスタマイズのコストが、中小企業の意思決定速度と噛み合わない」というものでした。1画面の変更に見積と稟議と数ヶ月を要するパッケージ導入の構造は、木工所の規模では最初から成立しません。

当社（大阪・八尾の木工所、株式会社コバヤシ）では、この前提を捨て、Odoo・PostgreSQL・FreeCADといったOSSを核に、Claude CodeというAIコーディングエージェントを実装の手として、基幹システムを自社で組み上げました。背景は[一般向けの記事](https://kobayashi-works.co.jp/digital/system-jidai-no-owari/)に書きましたが、本稿では実際にどう構成し、どこで設計判断を下し、どこでつまずいたかを技術的に掘り下げます。

## システム構成の全体像

当社の基幹システムは、業務基盤・会計連携・設計・インフラの4層で構成しています。業務基盤はOdooで、見積→受注→請求→経費を一元管理します。会計連携は、スキャンした領収書をAIが読み取り・分類し、会計ソフトへ渡すパイプラインです。設計はFreeCADで、全操作をプログラムから扱えるAPIを持つため、将来の設計自動化の土台として選定しました。インフラは社内サーバーを自社構築し、事務所と工場を暗号化された閉域網で接続、データは毎日自動バックアップしています。

この構成で意識したのは「単一のシステムに全部を詰め込まない」ことです。Odooは業務トランザクションの記録に専念させ、書類整理や日次レポート配信、サーバー監視といった定型作業は、常時稼働する複数の小さなAIエージェントに分担させています。モノリシックな仕組みに寄せるより役割ごとに独立させたほうが、後からClaude Codeに「この部分だけ直して」と指示しやすく、変更の影響範囲も読みやすくなります。

## 実装の要点1: Odooの日本向け帳票カスタマイズ

Odooは海外製のERPなので、標準のままでは日本の商習慣に合う帳票になりません。当社では見積書・請求書のレイアウトや税区分の扱いを、QWeb（Odooの帳票テンプレート言語)とPythonのモデル拡張で作り込みました。たとえば消費税の端数処理を明細ごとではなく請求書単位で丸めたい場合、標準ロジックを継承モデルで上書きします。

```python
from odoo import models

class AccountMove(models.Model):
    _inherit = "account.move"

    def _get_tax_totals(self):
        # 明細ごとではなく請求書単位で消費税を丸める
        totals = super()._get_tax_totals()
        totals["amount_tax"] = round(totals["amount_untaxed"] * 0.10)
        return totals
```

こうした拡張は、Odoo本体を直接書き換えず、継承（inherit）で差分だけを足す形にしています。理由は単純で、Odooのアップデート時に自作部分が上書きされて消えるのを避けるためです。パッケージ時代なら「カスタマイズ内容をベンダーに申請し直す」作業だったものが、継承モジュールを1つ足すだけで完結します。前職でのカスタマイズ交渉の経験があったからこそ、最初から「本体に手を入れない」方針を徹底できました。

## 実装の要点2: 領収書OCR→会計連携パイプライン

経費精算は、紙の領収書をスキャンし、AIが金額・日付・勘定科目を読み取って分類し、会計ソフトへ渡す流れにしています。ポイントは、AIの読み取り結果をそのまま確定させず、構造化データとして一度中間フォーマットに落とし、人が確認できる形にしてから連携する点です。

```python
import anthropic

client = anthropic.Anthropic()

def classify_receipt(image_bytes: bytes) -> dict:
    response = client.messages.create(
        model="claude-sonnet-5",
        max_tokens=512,
        messages=[{
            "role": "user",
            "content": [
                {"type": "image", "source": {"type": "base64", "data": image_bytes}},
                {"type": "text", "text": "領収書から日付・金額・支払先・勘定科目候補をJSONで出力して"},
            ],
        }],
    )
    return parse_json(response.content[0].text)
```

分類結果は一旦レビュー用のキューに溜め、確度が高いものだけ自動で会計ソフトへ渡し、判断が割れそうなものは人が確認してから確定させます。経費の勘定科目は税務上の判断が絡むため、AIの誤読を無条件に信用するリスクのほうが確認作業の手間より大きいと判断しました。自動化は「作業を消す」ためではなく「判断すべき部分だけ人に残す」ために使う、という線引きです。

## 運用して分かった設計判断の勘所

半年以上運用して見えてきたのは、AIエージェントを常時稼働させる上での「権限設計」の重要さです。書類の自動整理やレポート配信を担うエージェントに、業務データへの書き込み権限をどこまで渡すかは、便利さと事故リスクのトレードオフになります。当社では、読み取り専用で完結する作業（日次レポートの集計・配信、サーバーの死活監視）と、書き込みを伴う作業（帳票生成、経費の仕訳登録）を明確に分け、後者は必ず人の確認を挟む運用にしています。

もう1つの学びはバックアップの検証です。毎日自動バックアップを取ること自体は簡単ですが、「取れているつもり」で実際には壊れているデータを掴まされるリスクは、内製システムでは特に高くなります。ベンダー製品なら保証されていた復旧手順を、自分たちで定期的にリストア試験するところまで含めて設計しないと、バックアップは安心材料になりません。前職でシステムの「導入」だけを見てきた立場からすると、内製の本当の難所は実装そのものより、こうした地味な運用規律の設計にあると感じています。
