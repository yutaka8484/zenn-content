## 記録が分散し、レビューが属人化する

製造業のDX担当は複数の仕事を並行させている。現場ヒアリング、設備データの取得検証、工程管理の小さな改善、そして最近はAIエージェントに定型作業を任せる試行。これらの記録は、気づけばチャット履歴、表計算、手元メモ、issueコメントへ散っていく。数日後に「あの検証の結論は何だったか」を思い出せず、同じ調査をやり直すことも珍しくない。

本質は、タスク・プロジェクト・実行ログという三つの層が別々の場所に置かれていることだ。タスクは「今日やること」、プロジェクトは「なぜやるか」、実行ログは「何を試して何が起きたか」を表す。これらが分離していると、日次の振り返りは記憶頼りになり、週次の計画は前週の実績と切り離された希望的観測になりやすい。担当者が休むと進捗が見えなくなる属人化も、ここから生まれる。

danielmiessler氏が公開しているLifeOSは、生産性ツールとAIエージェントを組み合わせて個人の作業基盤を作る構想だ。公開情報を読む限り要点は「プレーンテキストで状態を持ち、AIから参照・更新できる形にしておく」ことにある。この考え方は、少人数で製造現場のDXを回すチームにも当てはめられるはずだ。以下、日次レビューと週次計画の仕組み化という観点で具体化する。

## LifeOSに学ぶ一元管理のディレクトリ設計

最初に決めるのは、三つの層をどこに置くかだ。LifeOSの公開情報ではモジュール化された構成とコンテキスト保持が特徴に挙げられている。最小構成で真似るなら、Gitリポジトリ一つにMarkdownを並べるだけで足りるはずだ。凝った仕組みより、AIエージェントがそのまま読める素朴なテキストを優先する。

```
lifeos/
├── projects/                 # なぜやるか。1プロジェクト1ファイル
│   └── 2026-mold-sensor.md
├── tasks/
│   ├── inbox.md              # 未整理の入力
│   └── today.md              # 今日の実行キュー
├── logs/agents/              # AIエージェントの実行ログ(日付別)
│   └── 2026-08-29.md
└── reviews/
    ├── daily/2026-08-29.md
    └── weekly/2026-W35.md
```

projectsには背景・完了条件・関連リンクだけを書き、進捗は書かない。進捗はtasksとlogsから毎日組み立てる。こうするとプロジェクト定義は数週間単位でしか変わらず、日々動くのはタスクとログだけになる。変更頻度でファイルを分けておくと集約スクリプトが単純になり、差分レビューもしやすい。

利点は特別なアプリが要らないことだ。エディタとGit、手元のAIエージェントがあれば動く。環境依存の情報はリポジトリに含めず環境変数か別管理とし、バックアップはGitのremoteに任せる。まず器を決め、運用しながら項目を足す方針なら、初期の作り込みで力尽きずに済むはずだ。

## AIエージェントの実行ログを構造化して残す

AIエージェントに作業を任せ始めると、「何を指示し、どのモデルが、何を出力し、結果どうだったか」が最も失われやすい。チャットUIの履歴は検索しにくく、数週間後には追えない。そこでエージェントを走らせるたびにlogs/agents/へ追記する。先頭にYAML frontmatterを置き、本文に所感を書く。

```markdown
---
date: 2026-08-29
project: 2026-mold-sensor
agent: claude-sonnet-5
task: 温度ログCSVの異常値抽出スクリプトを書かせる
outcome: partial        # done / partial / failed
follow_up: 閾値のハードコードをやめ設定ファイル化する
---

外れ値の判定ロジックは妥当。ただし欠測行の扱いが未考慮で、
そのまま現場データに通すとエラーになる。次回プロンプトに前提を追記。
```

構造化する理由は三つ。第一に、outcomeとfollow_upを定型フィールドにしておくと、日次レビューで未処理のfollow_upを機械的に拾える。第二に、実行日とprojectで紐づくため、週次計画のときにプロジェクト単位で試行回数と成果を並べられる。第三に、後からトークン量やコストの列を足せば、どの作業に負荷が偏るかを月次で見直せる。

frontmatterは最初から完璧を目指さず、振り返りで「この情報があれば」と思ったものを足す。LifeOSの掲げるコンテキスト保持も、後から参照できる形で残すことだと解釈すれば、テキスト一枚で始められるはずだ。

## 日次レビューと週次計画をスクリプトで仕組み化する

仕組み化の肝は、レビューを「やる気」ではなく「コマンド一つ」で始められる状態にすることだ。当日のタスクとエージェントログを一つの雛形に集約するスクリプトを用意する。

```bash
#!/usr/bin/env bash
# bin/daily-review.sh
set -euo pipefail
DAY=$(date +%F)
OUT="reviews/daily/${DAY}.md"

{
  echo "# 日次レビュー ${DAY}"
  echo -e "\n## 今日のタスク"
  cat tasks/today.md
  echo -e "\n## エージェント実行ログ"
  grep -l "date: ${DAY}" logs/agents/*.md 2>/dev/null | xargs -r cat
  echo -e "\n## 未処理の follow_up"
  grep -h "follow_up:" logs/agents/*.md | sed 's/^/- /'
  echo -e "\n## 明日に送るもの / 気づき"
} > "$OUT"
echo "created ${OUT}"
```

これを毎営業日の終業前に走らせ、生成された雛形に3分だけ追記する。機械が集める部分と人間が考える部分を分けたのが要点で、集計は自動、判断は手動。これなら疲れている日でも続く。

週次計画は月曜の朝に`reviews/weekly/2026-Wxx.md`を作り、前週の日次レビューから「明日に送るもの」を集めて初期リストにする。Makefileのターゲットにしておけば`make weekly`で下準備が終わるはずだ。前週の実績が必ず目に入るので、計画が願望に寄りすぎない。この雑務自体をエージェントに任せることもできるが、まず手で回して手順を固め、安定してから自動化する順序を勧めたい。

## まとめ:小さく始めて、更新し続ける

ここで示したのは新しい製品の導入ではなく、すでに散らばっている記録の置き場所と見返し方を決めるだけの運用設計だ。projects・tasks・logsの三層をGitリポジトリのMarkdownに集め、AIエージェントの実行ログをfrontmatterで構造化し、日次レビューと週次計画をスクリプトで下ごしらえする。この三点がそろうと、振り返りは記憶頼みでなくなり、週次計画は前週の実績の上に立つ。

LifeOS自体は発展途上の公開プロジェクトであり、そのまま製造現場に載せるには検証がいる。ただ「プレーンテキストで状態を持ち、AIから読み書きできるようにする」という中心の考え方は、少人数でDXを回す組織ほど効くはずだ。ツールが増えるほど記録は分散するので、器はできるだけ素朴にしておきたい。

始め方としては、今週の日次レビュー用ディレクトリを作り、今日の作業ログを一件だけ手で書いてみるのがよい。運用しながら足りない項目を足していけば、数週間で自分の仕事に合う形に育つ。完成形を先に設計しようとしないことが、この種の仕組みを続ける最大のコツだと考えている。
